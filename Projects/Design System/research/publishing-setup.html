Public sharing is go. Two minutes of setup, then one link that lasts.

The ruling, Mark, quoted: “Update HQ and keep going to facilitate public sharing.” That settles the question the four routes hung on: a Re.SOURCE page may be readable by anyone who has the link. Route 1 is the way, and the vault side of it is already built and tested – the copy list, the publish script, the link checker and the workflow all live in the repo now.

What is left is the one part no session can do for you: the public repository has to be created by your GitHub account, and only your account can create it.

That is GitHub's permission model, not a workaround being routed around you. A session's GitHub key is scoped to the repository it is granted — this one reaches the vault and nothing else, which is exactly why the vault has stayed safe. On 20 September both directions were tested and the platform proved to be one repo per session (the site session writes the site repo, the vault session writes the vault). Two minutes below wires the hands-off bridge, and after that every publish is one click.

Step 1

Create the empty public repo

About a minute

Repository name
Re.SOURCE-Site – typed exactly. If you would rather it were called something else, that is fine: tell the session the name and the script and workflow change in one line each.

Step 2

Give automation a key (the smart path)

One minute, hands-off after

Arena grants one repo per session — tested both ways on 20 Sep (vault sessions see only Re.SOURCE, site sessions see only Re.SOURCE-Site). That is a platform limit, not a scope to widen by reconnecting. So publishing does not run from a session's own key; it runs from Actions with a stored credential you add once.

Smartest: deploy key
No expiry, least privilege (only the site repo, only write). On your Mac where gh is logged in as you:
bash Projects/Publish/setup-auto.sh
It generates an ed25519 pair, adds the public half as a write deploy key on Re.SOURCE-Site and the private half as the Actions secret SITE_PUSH_KEY on Re.SOURCE. Rerunning it replaces the pair cleanly.
Also works: fine-grained PAT
bash Projects/Publish/setup-auto.sh --pat prints the exact steps. Same scope, but it expires (up to 365 days) and is tied to your user token.
Where to check
Site repo → Settings → Deploy keys (should show “Re.SOURCE publish”, write). Vault repo → Settings → Secrets and variables → Actions → SITE_PUSH_KEY (or SITE_PUSH_TOKEN).
What was wrong with “reconnect both”
That was the assumed path until both sessions were tested. Reconnecting Arena does not offer two repos — each connection stays single-repo. The key step above replaces it.
Step 3

Only if needed

The workflow pushes the mirror; Pages needs to be on once. If your PAT has Pages: write, the workflow can enable it; otherwise it is one click.

One click

Cost
Nothing. A public repo serves Pages on the free plan.

What goes public, and what stays private

Public, the moment you publish
The hub pages (HQ, Masters, Notes), the seven masters, the routes decision page and this runbook, and everything they run on: styles, tokens, scripts, self-hosted fonts with their licences, component sources, the card data, and the six captures HQ embeds. All of it is listed, file by file, in Projects/Publish/manifest.txt – a plain text file you can read and cut down at any time. Trimming it and republishing is one session command.
Private, always
Everything not on that list: the vault rules, the handover, the queues and prompts, session notes, the weekly folders (apart from those six captures), word-source exports, tests, scraps and internal screenshots. The site repo never sees them.
The one known trade-off
HQ carries a few links to markdown files – the queue, the prompts, the rules. On the public mirror those links dead-end, on purpose: markdown is session memory and never goes public. The pages are for looking at, and everything you look at is fully there. If the dead links ever bother you, a follow-up lane can take them off the HQ page itself.

How publishing works once it exists

The mechanism, in plain words

The site repo is a mirror of a named list of files, at the same paths as in the vault – that is what keeps every relative link, font and image working without touching a page. The root of the site is a small redirect onto HQ.

Three commands do everything, and they live in Projects/Publish/publish.sh: stage copies the manifest set, check verifies that every local reference in every staged page resolves (a missing asset fails the publish loudly instead of serving a broken page; the markdown trade-off above is reported, not failed), push mirrors the result onto the site repo. A stamp file at the site root records which vault commit the mirror was made from.

There is also a GitHub workflow (.github/workflows/publish-site.yml) that runs the same three steps on demand once a deploy key or token is added to the vault's secrets — the step you just ran above. Dispatch it from the Actions tab (Publish site → Run workflow) and it does stage → check → push without any session. The link stays the same forever either way; republishing changes the pages behind it, never the address. Until the key exists, the workflow reports and stops at the push, and bash Projects/Publish/publish.sh remains usable in a session that has been granted the site repo.
