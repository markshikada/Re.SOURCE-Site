Ultrawork

What it actually changes on this machine, measured against the sessions where it was off.

Ultrawork is one instruction file, 552 lines, that the agent reads instead of guessing how careful to be. It is not a smarter model and not new tools. So the only honest question is what it changes. That is answerable: 96 sessions ran on this machine between 30 September and 3 October, and 14 of them had the directive engaged.

The measured answer, first

Most of what the file asks for already happened without it. Phased checklists, file edits, evidence language, PASS and FAIL wording: all present in the sessions where ultrawork was off. Three things survive the comparison, and only the first is large: it registers a goal (79% against 25%), it batches edits into one call (36% against 4%), and it commits more (64% against 33%).

01Engaged against not engaged, at equal size

Raw counts flatter the mode wildly, because engaged sessions are far bigger. Comparing only sessions with real work in them (20 or more tool calls: 14 engaged against 24 not engaged) is the honest cut.

What it genuinely adds

  • A contract. A goal with pass and fail criteria, written before the work, so "done" stops being a feeling.
  • Batching. Independent changes go out as one call, which is why the feed shows one line instead of seven.
  • Landing it. Roughly twice the commit rate, so the work survives the session.

What it only asks for

  • Evidence, phased tracking, verification language, cleanup receipts, tier triage, no polling loops. All of it is house style already, enforced by the standing instructions whether or not this file was read.

02Is it worth it

Worth it when the work has an arguable definition of done: multi-file builds, migrations, refactors across a boundary, anything touching auth, sessions, permissions or money. Not worth it for a question, a lookup or a one-spot fix, and the file itself agrees: its LIGHT tier exists precisely so small work skips the heavy machinery. The cost is real too. It reads 552 lines, it plans before it acts, and on one occasion it produced process text instead of an artefact (session 01a10133, 61 tool calls, zero commits, the promised work never done).

03How it is switched on

There is no configuration toggle anywhere: a search of omo.jsonc for ultrawork, ulw or directive returns nothing. It binds when that file has been read. A live process on this machine is running omo ulw as its own launch mode, which is the same thing arriving from the command line rather than the chat.

04Your default, as of 3 October 2026

Two instruction files already declared ultrawork the default. What was missing was any way to execute that, so the read never happened and you had to ask. Three defects, all fixed today:

DefectWasNow

The rule lives in ~/.omo/agent/AGENTS.md, which every session on this machine reads at start:

ls -d ~/.omo/binary-runtime/*/plugin/skills/ultrawork/SKILL.md | sort -V | tail -1

Verified here: that prints exactly one readable path, and the clauses are present on read-back. The instruction now also says that a prose mention is not compliance; the file has been read or it has not. You will not have to ask again.

05Two things found on the way

A claim that did not hold. Session 01a1019f reported it had set the thinking level to high and closed with "done, high on both seats". The file now reads low for that seat. Something reset it after the session, and the report does not survive contact with the file.

Evidence language is a false friend. The word "evidence" appears in every engaged session and in 63% of substantial unengaged ones. Its presence proves nothing about the mode.
